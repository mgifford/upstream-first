# Contributing

Contributions can include issues, reproductions, tests, documentation,
translations, design work, standards analysis, policy review, code, and
maintenance.

## Before contributing

1. Read the charter, Code of Conduct, security policy, and AI contribution
   policy.
2. Search existing issues and pull requests.
3. Check whether the project is accepting the proposed kind of change.
4. Open a design issue before substantial, cross-skill, or breaking work.
5. Use a private security report for suspected vulnerabilities.

## Classify the change

State:

- the observed problem or requested outcome;
- who is affected and how;
- whether it is a bug, feature, design question, maintenance task, policy
  change, security issue, accessibility defect, or instance-specific need;
- the evidence supporting that classification;
- the likely owner and alternatives considered.

Classification is provisional until maintainers confirm it.

## Keep contributions reviewable

- Address one coherent problem.
- Include the smallest sufficient change.
- Add or update tests when behaviour changes.
- Update affected documentation and examples.
- Explain trade-offs and unresolved questions.
- Separate required changes from optional improvements.
- Do not mix broad formatting or refactoring with a functional change.
- Remain available for review and revision.

Review comments should distinguish:

- **Must:** required for correctness, policy, security, compatibility, or
  acceptance.
- **Should:** important improvement that may be resolved here or in agreed
  follow-up work.
- **Consider:** optional suggestion.

## AI-assisted contributions

Follow [AI_CONTRIBUTION_POLICY.md](AI_CONTRIBUTION_POLICY.md). Disclose material
AI assistance in the pull request when required by that policy. The human
contributor remains responsible for every submitted statement and change.

Do not submit agent-generated comments, reviews, issues, or pull requests
without human review and approval.

## Standards

Use the current applicable stable standard unless compatibility, receiving
project policy, or law requires another version. Name the exact version when a
claim depends on it. See [references/STANDARDS.md](references/STANDARDS.md).

## Pull-request checklist

- [ ] The issue or rationale is linked.
- [ ] The change is within agreed scope.
- [ ] Project policy and standards were checked.
- [ ] Tests and repository validation pass.
- [ ] Accessibility, security, privacy, licensing, and sustainability impacts
      were assessed.
- [ ] Documentation and examples match the final change.
- [ ] Material AI assistance is disclosed when required.
- [ ] The contributor can explain and maintain the work.
- [ ] No confidential information, credentials, or personal data are included.
